# 作品案例：把“相关资料”变成有依据的排错建议

作者：周曜宇｜北京邮电大学数学硕士在读

类型：个人 AI 应用实践｜场景：技术学习与部署排错

## 1. 用户问题与产品目标

在学习 Docker Compose、数据库连接和事务处理时，用户常常能找到官方文档，却难以判断哪条规则适用于自己的环境。随着对话继续，用户又会补充日志、纠正部署位置，或讨论尚未实施的方案。直接把最近几条聊天内容交给模型，容易出现三类问题：

1. 找到的资料很相关，但只回答了“为什么”，遗漏“怎么处理”。
2. 把“如果迁移到容器”误认为“已经迁移”，从而给出错误的连接地址。
3. 资料或现场信息不足时，仍给出确定根因，或反复要求用户提供已经无法取得的日志。

我的目标是让助手帮助用户理解规则、明确下一步排查动作，并看得见回答依据；无法判断时，具体说明缺少什么。项目目前面向学习场景，没有实际教学平台接入或教育用户试用数据。

## 2. 本人负责部分与 AI 协作方式

我参与场景拆解、需求与证据标注、架构关键取舍、输出验收和实验分析。AI 辅助完成实现细节、部分测试与复核。我不是只运行演示，而是在关键节点提出方案、分析反例，再用保存状态和验证记录检查方案是否成立。

| 我参与的决策 | 如何具体落实 | 验证关注点 |
| --- | --- | --- |
| 原始问题与检索词分别保存 | 改写词供检索使用，评价与生成仍以原始问题为依据 | 不因改写而丢掉用户真正想问的后半部分 |
| 实际环境与假设分开 | 保存分析范围、原话来源及实际环境；未确认的条件不直接覆盖事实 | 假设后切回实际时，仍能恢复正确的连接路径 |
| 纠正只改相关字段 | 应用位置更新时保留未变化的服务名、端口映射 | 不因修正位置而丢失旧消息中仍有效的信息 |
| 避免迟到回答覆盖新输入 | 运行固定输入版本；提交时检查当前版本、活跃尝试和租约 | 新输入到达后旧结果只进入历史 |
| 区分重选证据和补检贡献 | 比对初检排名、最终引用及新增证据，避免把所有改善归于补检 | CP01 中两个结论分别来自不同环节 |

可核对的本人分析示例保存在 [case-records.json](../evidence/case-records.json) 的 `user_contribution_examples` 中；这些是已有对话中的设计与分析，不是新编造的工作经历。

## 3. 问题一：检索相关，回答仍漏关键点

**发现问题。** TX02 询问“已成功提交、没有新 SQL 或新事务，再次调用 `commit()` 会怎样”。初检资料中已有直接规则，但排在第 5 位。只取前三条时，模型缺少确认无活动事务下行为的直接依据。

**处理方法。** 让评价器检查回答需求与证据的对应关系，再由控制器决定是否重新选证、补检或停止。不能看到回答不完整就直接换检索模型：先判断关键证据是否已经在候选池里。

**验证方式。** 两组使用相同问题、初始候选、知识库版本、生成模型与回答提示词。A 直接使用 RRF 前三条；B 先评价覆盖情况再选择证据。B 选中第 2、5 条，回答覆盖了该条件下的 no-op 行为；两组均没有补检。

**得到的认识。** 本题的改善来自选证；B 也多了一次模型请求，记录耗时从 9.06 秒增加到 25.51 秒。这不是“全面提升准确率”的证据，而是一个可以解释原因、同时看到代价的具体改进。[对比数据](../evidence/case-records.json)

## 4. 问题二：多轮追问混淆实际与假设

**发现问题。** 用户实际把应用运行在宿主机，数据库在 Compose 中，端口映射为 `5433:5432`。讨论“以后迁移到同一个 Compose 网络”时，若直接覆盖当前环境，之后询问实际配置就可能误答 `db:5432`。

**处理方法。** 原话、任务、环境状态和假设范围分别保存。模型提出结构化更新，后端检查字段、来源与版本后再保存。讨论假设时只改变本轮分析范围，用户明确确认后才更新对应环境陈述；不把助手的建议当成用户事实。

**验证方式。** 设计五轮：实际部署 → 提出假设 → 承接假设 → 回到实际 → 确认实施。除了读最终回复，还核对每轮输入版本、实际应用位置、分析范围、服务名、两种端口和来源消息。[完整五轮记录](../evidence/multiturn-dialogue.md)

**得到的认识。** 会话记忆应保留“这句话在什么条件下成立”。来源存在只能证明提取内容来自某句话，不能单独证明模型理解正确，因此仍需要纠正、指代和条件表达的测试。

## 5. 问题三：执行成功不等于有资格发布为最新回答

**发现问题。** 模型调用较慢。M1 运行时，用户可能又发来 M2 纠正部署位置。如果保存前仅在 Python 中读一次版本，随后再写库，中间仍可能插入新消息。

**处理方法。** 原话先保存，准备状态通过校验后用短事务提交；模型调用在事务外执行。一次运行固定输入与知识库版本，结束时在事务内核对当前版本、活跃 `attempt_id` 和租约。迟到结果保留作历史，不覆盖最新状态。

**验证方式。** 对同消息重复提交、内容冲突、旧尝试迟到、租约接管、进程恢复和版本固定进行隔离测试。源码可从 [会话服务](../app/conversation_service.py)、[尝试管理](../app/conversation_attempts.py) 和 [对应测试](../tests/test_conversation_attempts.py) 查看。历史 PostgreSQL／HTTP 测试 90 项通过；本次公开导出仅重跑了离线部分。

## 6. 如何核验，而不只相信模型回答

验证分三个层次：

1. **结构与状态：** 标识、来源、输入版本、候选范围是否合法；旧任务是否混入新任务信息。
2. **证据与语义：** 每个关键结论有无支持；是否区分通用规则和具体故障根因；有没有遗漏问题后半部分。
3. **代价与适用范围：** 记录调用次数、耗时、是否补检；标明固定开发集与当前未解决问题。

已有材料包括 15 题单轮对比、10 个多轮场景共 30 轮，以及状态／来源／回放检查。它们是开发与回归材料，部分评分由 AI 辅助，不能代替真实用户试用和独立评测。[证据索引](../evidence/README.md)

## 7. 与教育岗位的联系

这个案例的已有价值在于：使用 AI 完成学习与项目任务，拆解复杂问题，把异常流程写清楚，并通过资料、状态与实验核验输出。这些工作与岗位要求的 AI 实践、逻辑表达、信息核实和跟进能力直接对应。

如果延伸到编程实验教学，我会先选择一门课程中的具体实验：

- 学生需要理解“为什么错、下一步查什么”；教师需要查看回答依据与资料适用范围。
- 首先接入教师审核的实验说明、课程资料和常见错误，沿用原问题、证据来源及多轮纠正机制。
- 用真实提问检查解释是否覆盖学习目标、是否误导、是否需要教师接管，再评估是否帮助学生理解。

以上是后续应用设计，尚未实施，不宣称已有课堂效果、教师采纳率或学习成绩提升。
